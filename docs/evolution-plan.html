Phraiz 1인 리빌드: 기능별 멀티 LLM 라우팅과 아키텍처 경량화 전략

SSU-IT-Contest의 프론트엔드(FE)와 백엔드(BE)를 분석한 결과, 기존 국내 논문 인용 파이프라인과 Next.js·Spring Boot 기반은 유지하되 단일 OpenAI 호출을 기능별 멀티 LLM 게이트웨이와 스트리밍 구조로 교체하고 3중 중복 스키마를 통합하는 것이 1인 개발 효율과 제품 완성도를 동시에 끌어올리는 최선의 경로입니다.

현재 코드베이스는 국내 학술 인용 자산이 탄탄하지만 1인 유지보수 병목이 뚜렷합니다

팀 프로젝트로 구축된 Phraiz는 대학생과 연구자를 겨냥한 AI 글쓰기 지원 플랫폼입니다. FE 레포지토리는 Next.js 14.2.30(App Router), TypeScript, Tailwind CSS, shadcn/ui, Zustand 5, TanStack Query 5, Toss Payments SDK 등 실무 표준에 가까운 현대적 스택으로 구성되어 있으며, (main-service) 라우트 그룹 아래 패러프레이징·요약·인용 생성 페이지를 깔끔하게 분리해 두었습니다.

BE 레포지토리 역시 Spring Boot 3.5.3(Java 17), MySQL, Redis, Spring Security + OAuth2(Google·Kakao·Naver)와 1회용 임시 토큰 교환 흐름까지 탄탄합니다. 특히 translation-server(Zotero Translation Server)에 국내 학술 DB 전용 파서(DbpiaAuthorParser, KissAuthorParser, KyoboAuthorParser)와 citeproc-java를 결합한 인용 파이프라인은 일반 LLM 래퍼 서비스와 차별화되는 핵심 자산입니다.

그대로 살려야 할 핵심 자산

  • 한국어 학술 인용 파이프라인: Zotero Translation Server + DBpia·KISS·교보스콜라 전용 저자 파서 + citeproc-java 조합은 비용이 0원이고 결정론적 정확도가 높습니다.
  • 모던 FE 생태계: Next.js 14 App Router, TanStack Query, Zod, shadcn/ui 조합은 스트리밍 UI와 에디터 확장에 바로 재활용할 수 있습니다.
  • 인증·결제 골격: Redis 기반 Refresh Token·이메일 인증·OAuth2 임시 코드 검증과 PaymentController의 토스페이먼츠 정기 구독 흐름이 이미 갖춰져 있습니다.

1인 전환 시 반드시 해소할 병목

  • 단일 OpenAI 동기 호출: 모든 AI 기능이 하나의 OpenAI API 동기 응답에 묶여 긴 텍스트 요약·패러프레이징 시 체감 대기 시간이 길고 모델별 비용 최적화가 불가능합니다.
  • 3중 중복 도메인 테이블: Paraphrase*, Summary*, Cite*가 각각 Folder–History–Content 3계층 엔티티를 복제해 CRUD 유지보수량이 3배로 불어나 있습니다.
  • PDFBox 텍스트 추출 한계: Apache PDFBox 2.0.27은 2단 구성 논문, 표, 수식, 스캔 PDF에서 문맥이 깨져 요약 품질을 떨어뜨립니다.
  • 토큰 원가 가드 부재: 정액 구독 결제(/api/payment/subscription)에 사용자별 토큰·크레딧 한도가 없어, 멀티 LLM 도입 시 헤비 유저 1명이 월 구독료를 초과하는 역마진이 발생할 수 있습니다.

기능별 특성에 맞춰 LLM을 분업 배치해야 비용과 품질을 모두 잡습니다

패러프레이징, 논문 PDF 요약, 인용 생성은 요구하는 모델 역량이 완전히 다릅니다. 하나의 플래그십 모델로 모든 요청을 처리하면 API 비용이 과도하게 발생하고, 반대로 저가 모델 하나로 통일하면 한국어 학술 문체 품질이 떨어집니다. 기존 ParaphraseController, SummaryController, CiteController의 역할을 기준으로 각 기능에 가장 유리한 모델과 보조 기술을 매핑하면 다음과 같습니다.

기능 (기존 API) 현재 구현 한계 추천 멀티 LLM 전략 핵심 도입 기술 기대 효과
AI 패러프레이징
/api/paraphrase		 OpenAI 단일 모델 동기 호출, 6개 모드·강도(0–100)를 프롬프트에만 의존 문체·학술 모드: Claude 계열
기본·유창성/무료 티어: 경량 고속 모델 분기		 SSE 실시간 스트리밍, Tone Blend 강도별 temperature + Few-shot 프리셋, FE 단어 단위 Diff 하이라이트 한국어 번역투 감소, 첫 토큰 응답 1초 이내 단축, 수정 근거 시각화

2차 폴백: 경량 모델 + OpenAI Structured Outputs		 CSL-JSON 스키마 강제 추출, Crossref REST API로 DOI·서지 실존 여부 교차 검증 인용 환각(가짜 논문) 원천 차단, 파싱 실패율 감소 및 저비용 유지

패러프레이징: 문체 일관성과 Diff UX

현재 standard, academic, creative, fluency, experimental 5개 엔드포인트는 URL을 쪼갤 필요 없이 단일 스트리밍 엔드포인트에 모드와 강도(0–100) 파라미터로 통합하는 편이 깔끔합니다. 한국어 학술·자연스러운 문체 변환에는 Claude 모델군을 우선 배치하고, 사용자가 어떤 단어가 왜 바뀌었는지 즉시 검수하도록 프론트엔드에 Diff 뷰어를 추가하세요.

PDF 요약: PDFBox 제거와 캐싱 전환

Gemini API 문서 이해 기능은 PDF를 이미지·레이아웃 단위로 직접 해석해 최대 1,000페이지까지 처리합니다. 사용자가 논문 1편을 올린 뒤 한 줄 요약(one-line)에서 핵심 키워드·섹션별 요약으로 모드를 여러 번 바꿀 때 Context Caching을 적용하면 매번 전체 논문을 재전송하는 낭비를 막을 수 있습니다.

인용 생성: 결정론 우선, LLM은 복구 전용

인용문 생성을 LLM에 통째로 맡기면 존재하지 않는 권·호수나 DOI를 지어내는 환각이 치명적입니다. 기존 translation-server와 DBpia·KISS·교보스콜라 파서 결과를 먼저 사용하고, 필수 필드가 비었을 때만 Structured Outputs로 웹페이지 본문에서 CSL-JSON을 추출한 뒤 Crossref REST API로 검증해 citeproc-java에 넘기는 하이브리드 파이프라인이 가장 안전합니다.

1인 개발자는 인프라와 데이터 모델을 먼저 단순화해야 오래 운영할 수 있습니다

팀 프로젝트 시절에는 프론트엔드와 백엔드 인원이 나뉘어 있어 Spring Boot + MySQL + Redis + Zotero 컨테이너 4개를 띄우는 구조가 합리적이었습니다. 혼자 리빌드할 때는 본인의 주력 기술 스택과 목표(취업용 백엔드 포트폴리오 vs. 빠른 SaaS 출시)에 따라 아래 두 경로 중 하나를 명확히 선택해야 합니다.

비교 항목 경로 A · Spring Boot 유지 + 멀티 LLM 게이트웨이 경로 B · Next.js 풀스택 통합 (백엔드 경량화)
추천 대상 Java/Spring 백엔드 역량을 어필하거나 기존 BE 인증·결제·국내 논문 파서 코드를 최대한 재활용하려는 경우 TypeScript 단일 언어로 개발·배포 속도를 극대화하고 서버 운영 부담을 최소화하려는 경우
멀티 LLM 연동 Spring AI 도입, 또는 OpenRouter·LiteLLM Proxy를 통해 OpenAI 호환 단일 인터페이스로 Claude·Gemini·GPT 호출 Vercel AI SDK의 streamText·generateObject로 프로바이더 1줄 교체 및 React 스트리밍 훅 직결
인프라·운영 비용 Docker Compose로 Spring Boot·MySQL·Redis·Zotero를 단일 VPS에 통합 배포 (초기 설정 필요, 트래픽 제어 유리) Vercel + Supabase(PostgreSQL)로 무중단 배포, Zotero만 소형 컨테이너(Fly.io/Cloud Run)로 분리 운영
주의할 트레이드오프 Spring AI 2.0 계열은 Spring Boot 4.x 정합성을 요구하므로, 현재 3.5.3 유지 시 OpenRouter/LiteLLM 게이트웨이 방식이 업그레이드 충돌 없이 훨씬 빠름 기존 Java 기반 citeproc-java 및 국내 논문 파서를 Node.js(citation-js 등)로 포팅하는 초기 공수가 발생함

9개 도메인 엔티티를 2개 테이블로 통합

현재 백엔드는 패러프레이징·요약·인용 각각에 Folder, History, Content 테이블을 따로 두고 있습니다. 1인 개발에서는 이를 workspace_folders와 workspace_items(item_type: PARAPHRASE | SUMMARY | CITE, 세부 결과는 JSON 컬럼 저장) 2개 테이블로 통합하세요. 폴더 이동·검색·삭제 API가 1세트로 줄어들고, 추후 통합 에디터에서 3개 기능의 작업물을 한 폴더에 묶어 보여주기 쉬워집니다.

구독 역마진 방지와 LLM 관측성

PaymentController의 월/연 구독 모델에 Redis 기반 월간 크레딧 차감 미들웨어를 반드시 붙이세요. 무료 티어는 일일 요청 제한과 경량 모델로 라우팅하고, 유료 Pro 티어만 Claude·Gemini 네이티브 PDF·대용량 컨텍스트를 열어야 합니다. 아울러 Langfuse를 연동하면 기능별 토큰 원가, 응답 지연시간, 사용자별 비용을 대시보드에서 실시간 추적하고 코드 배포 없이 프롬프트 버전을 롤백할 수 있습니다.

분리된 3개 페이지를 하나의 학술 글쓰기 워크스페이스로 엮고 4단계로 실행하세요

기능별 LLM 교체만큼 중요한 발전 방향은 사용자 흐름(UX)의 연결입니다. 현재 FE는 /ai-paraphrase, /ai-summarize, /create-citation이 독립 페이지로 나뉘어 있어 사용자가 논문을 요약한 뒤 본문을 다듬고 인용을 넣으려면 탭을 오가며 복사·붙여넣기를 반복해야 합니다. 최종 단계에서는 좌측 논문 PDF 뷰어·요약 패널, 중앙 글쓰기 에디터(드래그 시 즉시 패러프레이징 + Diff), 우측 원클릭 인용 삽입이 이어지는 통합 캔버스를 목표로 삼으면 기존 단순 도구에서 리서치 워크스페이스로 격상됩니다.

단계 (기간) 핵심 목표 구체적 실행 항목 완료 검증 기준
Phase 1
1–2주차		 개발 환경 단일화 및 LLM 게이트웨이 구축 비어 있는 FE README.md와 .env.example 정비, 로컬 Docker Compose 1명령 실행 구성, OpenRouter 또는 LiteLLM 게이트웨이 연결, 패러프레이징·요약 API를 SSE 스트리밍으로 전환 코드 수정 없이 환경변수만으로 호출 모델 교체 및 실시간 타이핑 출력 확인
Phase 2
3–4주차		 기능별 특화 LLM 파이프라인 고도화 패러프레이징에 Claude 라우팅 + FE 단어 단위 Diff 뷰어 구현, SummaryController의 PDFBox를 Gemini Native PDF + Context Caching으로 교체, CiteController에 Crossref 검증 + Structured Outputs 폴백 추가 2단 논문 PDF 요약 품질 개선, 미등록 URL 인용 파싱 성공률 상승 확인
Phase 3
5–6주차		 도메인 통합 및 비용·과금 안전장치 3중 Folder–History–Content 스키마를 단일 워크스페이스 모델로 마이그레이션, Redis 크레딧 한도 + 토스페이먼츠 티어별 모델 분기 적용, Langfuse 트레이싱·프롬프트 버전 관리 연동 무료/유료 티어별 요청 차단 동작 및 Langfuse에서 기능별 USD 원가 조회
Phase 4
7–8주차		 통합 학술 에디터 UX 확장 요약된 논문 문장을 드래그해 즉시 패러프레이징하고 해당 논문 인용(APA/MLA/Chicago)을 본문에 자동 삽입하는 통합 워크스페이스 화면 구축, 주요 프롬프트 회귀 평가셋 구성 논문 업로드부터 인용 포함 초안 완성까지 단일 화면에서 이탈 없이 완료

모든 기능에 비싼 LLM을 붙이는 것보다, 무료 결정론적 파서(인용)와 특화 모델(문체·PDF)을 게이트웨이 뒤에서 정확히 분업시키는 설계가 1인 AI 서비스의 생존력을 결정합니다.
